# Архитектура

Проект делается как desktop-приложение на Python и PySide6.

## Цель архитектуры

Архитектура должна оставаться простой, чтобы приложение не превратилось в
перегруженный календарный комбайн.

## Планируемые слои

- `ui` - главное окно, закрепленная правая панель, календарная сетка, действия пользователя.
- `domain` - модель события и будущие правила предметной области.
- `services` - прикладные операции над событиями, которые связывают доменную логику и storage.
- `storage` - локальное сохранение данных в SQLite.
- `sync` - будущая синхронизация через GitLab.

## Текущая структура проекта

- `main.py` - точка запуска приложения.
- `domain/clock.py` - получение текущего времени.
- `domain/event.py` - модель события.
- `domain/event_limits.py` - ограничения длины полей события.
- `domain/event_status.py` - статусы событий и связанные с ними цвета интерфейса.
- `domain/event_factory.py` - создание новых событий и копий событий.
- `domain/event_index.py` - сортировка, индексация, поиск событий по `id` и пересечениям дат.
- `domain/event_update.py` - применение снимка события к существующему событию.
- `domain/history_manager.py` - управление стеками undo и redo.
- `services/event_service.py` - операции добавления и удаления событий через storage.
- `storage/event_storage.py` - работа с SQLite.
- `ui/calendar_window.py` - главное окно календаря.
- `ui/calendar_window_state.py` - начальное состояние главного окна.
- `ui/calendar_window_widgets.py` - создание виджетов главного окна.
- `ui/calendar_window_connections.py` - подключения сигналов главного окна.
- `ui/calendar_window_layout.py` - сборка layout главного окна.
- `ui/calendar_shortcuts.py` - горячие клавиши главного окна.
- `ui/calendar_grid.py` - кастомная сетка календаря с выбором времени мышкой.
- `ui/calendar_header.py` - заголовок дней недели над календарной сеткой.

Создание и редактирование событий выполняются через закрепленную правую панель
в `ui/calendar_window.py`, без всплывающих диалоговых окон.

## Календарная сетка

Сетка рисуется вручную через PySide6 `QWidget`.
Это нужно, чтобы поддержать поведение как в FullCalendar:

- выбор диапазона мышкой;
- шаг 30 минут;
- будущий drag-and-drop;
- будущее изменение длительности события за край блока.

## Модель события

Текущая модель события уже должна хранить не строку и колонку таблицы, а реальные
данные планирования:

- `id` - уникальный идентификатор события;
- `title` - название события, максимум 80 символов;
- `start_at` - дата и время начала;
- `end_at` - дата и время окончания;
- `note` - заметка, привязанная к событию, максимум 1000 символов;
- `status` - статус события;
- `created_at` - дата создания;
- `updated_at` - дата последнего изменения.

Одинаковые названия событий разрешены. Уникальность должна быть только у `id`.

Строка и колонка календаря считаются временной частью интерфейса. Они должны
вычисляться из `start_at`, а не храниться как главные данные события.

Индексация событий для быстрого поиска по `id`, датам и пересечениям диапазонов
находится в `domain/event_index.py`. UI-слой может хранить готовые индексы, но
не должен заново реализовывать правила overlap-поиска.

## Хранение данных

Текущий прототип использует SQLite.

Файл базы данных называется `calendar.db` и хранится в пользовательской директории:

```text
~/.local/share/calendar-planner/calendar.db
```

Если задана переменная окружения `XDG_DATA_HOME`, приложение использует путь:

```text
$XDG_DATA_HOME/calendar-planner/calendar.db
```

Старый файл `calendar.db` из корня проекта автоматически переносится в новое место при первом запуске,
если в новой директории базы еще нет.

Причины:

- надежнее, чем один JSON-файл;
- удобно искать события по датам;
- проще обновлять отдельные события;
- проще подготовить будущую синхронизацию.

## Таблица `events`

В SQLite используется таблица `events`.

Поля:

- `id` - уникальный идентификатор события;
- `title` - название события;
- `note` - заметка;
- `start_at` - дата и время начала в ISO-формате;
- `end_at` - дата и время окончания в ISO-формате;
- `created_at` - дата создания в ISO-формате;
- `updated_at` - дата последнего изменения в ISO-формате;
- `status` - статус события.

Старые базы без поля `status` обновляются автоматически при запуске приложения.
